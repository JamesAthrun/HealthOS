# HealthOS MVP Sprint 与上线计划

## 1. 计划目标

本计划把 HealthOS MVP 拆成可以逐步验收的小批次，覆盖：

- 产品和安全决策；
- 本地开发与自动化测试；
- MVP 六项核心能力；
- Docker 化和单服务器部署；
- 备份、恢复、监控和邀请制试运行。

本阶段只制定计划，不实施代码或生产部署。

## 2. 基准假设

- 团队规模：1 名主要开发者，必要时使用 AI 辅助开发与评审。
- Sprint 长度：Sprint 0 和上线 Sprint 各 1 周，其余 Sprint 各 2 周。
- 理想总周期：16 周开发和上线准备，之后 4 周邀请制试运行。
- 如果每周投入少于 20 小时，预计将每个 2 周 Sprint 延长至 3–4 周。
- 产品形态：Next.js PWA + FastAPI 模块化单体 + PostgreSQL + 私有 S3/MinIO。
- 部署形态：一台 Linux 服务器，Docker Engine + Docker Compose；AI 使用外部 Provider Adapter。
- MVP 用户：项目所有者和少量受邀家庭成员，各自独立账号，默认互不可见。

## 4. Sprint 详细计划

## Sprint 0：决策与验收基线（1 周）

### 目标

在写代码前确定会影响数据流和部署的关键选择，避免中途更换身份、数据地域或 AI Provider。

### 工作项

> 已完成的决策见 [DECISIONS.md](DECISIONS.md)。下列已标注 ✅ 的项目已完成。

- ✅ 确定服务器地域：中国大陆（云厂商和具体地域待定）。
- 确定域名、DNS 管理方和 TLS 方案，**启动 ICP 备案**（周期较长，位于上线关键路径）。
- ✅ 确定 OIDC：自托管 Logto，BFF 会话架构，邀请制注册。
- ✅ 确定首个 AI Provider：DeepSeek；数据保留和训练条款待核实。
- ✅ 确定对象存储：自托管 S3 兼容存储；异地云对象存储加密备份。
- 确定境内邮件发送服务（Logto 验证码、邀请邮件）。
- 确认 RPO 24 小时、RTO 4 小时和 D-014 保留期限。
- 把 MVP 页面流程画成低保真线框：登录、首次使用、今日、记录、建议、设置。
- 建立测试用户、合成健康数据和 AI 安全评估样本规范。
- 建立 Definition of Ready、Definition of Done 和发布风险清单。

### 本地验证

- 用两个合成用户走读所有用户故事，确认没有隐式家庭共享。
- 用数据流图逐项标记数据所在地域、处理方、保留期和删除路径。
- 评审服务器故障、AI 故障和身份服务故障的用户体验。

### 完成条件

- 5 个关键部署决策有书面记录和负责人。
- PRD 的 P0 项均有可测试验收标准。
- 不再存在“先开发再决定”的高影响数据流问题。

## Sprint 1：本地工程与容器基础（2 周）

### 目标

建立可以重复启动、测试和销毁的本地环境；此时只做工程骨架，不做健康业务功能。

### 工作项

- 初始化 frontend、api、worker 三个应用进程的工程骨架。
- 为 PostgreSQL 和 MinIO 建立仅限内部网络的本地服务。
- 区分开发 Compose 与未来生产 Compose overlay。
- 建立配置校验、Secret 占位、数据库迁移骨架和健康端点。
- 建立统一的格式检查、类型检查、单元测试、集成测试入口。
- 建立 CI：依赖安装、迁移、测试、Secret 扫描、依赖和镜像扫描。
- 建立结构化日志、request ID 和敏感字段脱敏测试。

### 本地测试

- 全新电脑/干净环境按 README 启动成功。
- 容器健康检查全部变为 healthy 后才运行依赖服务。
- 停止并重启应用后，数据库和对象存储测试数据仍存在。
- 删除本地测试卷后可以从零初始化，不依赖人工修库。
- `.env`、测试上传和数据库卷未出现在 Git 状态中。
- 日志中不出现密码、Token 或完整请求正文。

### 完成条件

- 一条标准命令可以启动本地栈，一条标准命令可以运行全部测试。
- CI 对主分支提交稳定通过。
- 容器镜像版本固定，不依赖不可预测的 `latest`。

## Sprint 2：身份、账号与数据隔离（2 周）

### 目标

先证明多用户安全，再允许任何健康数据进入系统。

### 工作项

- OIDC 登录、退出、会话过期和内部用户映射。
- 用户时区、locale 和最小账号设置。
- 应用层 owner-scoped repository 查询模式。
- PostgreSQL 运行时角色、迁移角色和 RLS 策略。
- 审计事件基础：登录、拒绝访问、敏感操作。
- 限流、CORS/CSRF 和统一无权响应策略。

### 本地测试

- User A 无法读取、修改、删除或判断 User B 的资源是否存在。
- 覆盖直接 ID、列表、批量接口、嵌套资源和后台任务五类越权路径。
- Token 过期、issuer/audience 错误、退出和撤销均被正确拒绝。
- RLS 在直接数据库集成测试中仍然阻止跨用户访问。
- API 运行角色确认不是表所有者且无 `BYPASSRLS`。

### 完成条件

- 横向和纵向越权测试 100% 通过。
- 代码评审确认任何业务查询都不能信任客户端提交的 `user_id`。
- 未通过本 Sprint 前，禁止进入真实健康记录开发。

## Sprint 3：档案与手工健康记录（2 周）

### 目标

在完全不依赖 AI 的情况下，完成最小可用的记录产品。

### 工作项

- 首次使用、健康档案和目标。
- 手工饮食及食物项 CRUD。
- 运动记录 CRUD。
- 睡眠记录 CRUD。
- 乐观锁、软删除、输入范围校验和审计。
- 手机优先的记录页面和基础无障碍行为。

### 本地测试

- API 单元与集成测试覆盖创建、查询、修改、删除和校验失败。
- 浏览器 E2E 覆盖首次使用和三类记录完整流程。
- 使用手机视口和真实手机局域网访问进行手动验收。
- 验证跨午夜睡眠、夏令时/时区切换、重复提交和并发修改。
- 验证用户删除后列表与统计不再读取软删除记录。

### 完成条件

- 用户不使用 AI 也能连续完成一整天的全部记录。
- 三类记录的错误提示明确，失败不会造成重复或半成品数据。
- 关键流程通过 Safari 与 Chrome 当前主版本测试。

## Sprint 4：私有文件与饮食 AI（2 周）

### 目标

完成“拍照—识别—人工修正—确认”的饮食闭环，同时保持手工录入可用。

### 工作项

- 私有上传会话、短期签名访问、文件元数据和生命周期。
- MIME/magic bytes、大小、像素、解码安全和 EXIF 清理。
- AI 处理同意和撤回的最小流程。
- Provider Adapter 与严格结构化饮食识别结果。
- AI 草稿、模型/模板版本和用户确认值分离保存。
- Worker 幂等、租约、有限重试和失败状态。

### 本地测试

- 正常图片、错误扩展名、畸形文件、超大文件和重复上传。
- User A 无法获得 User B 文件的下载 URL。
- 对象存储和 AI 分别停机时，手工饮食记录仍可使用。
- 同一任务重复执行不产生重复食物项或重复计费。
- 低置信和解析失败不直接进入正式统计。
- 用合成餐食图片评估识别和用户修正流程，不使用家庭真实照片。

### 完成条件

- 未经用户确认的 AI 结果不会进入看板统计。
- 文件始终私有，短期 URL 到期后失效。
- 撤回 AI 同意后不再创建新的外部处理任务。

## Sprint 5：今日看板与 7 天趋势（2 周）

### 目标

把记录转化为易懂但不过度医疗化的反馈。

### 工作项

- 今日饮食、运动、睡眠概览。
- 最近 7 天趋势和目标完成情况。
- 数据缺失和记录完整度提示。
- 所有统计只读取用户确认且未删除的数据。
- 移动端信息层级、加载状态、空状态和无障碍优化。

### 本地测试

- 使用固定合成数据验证每个聚合数值。
- 验证用户本地日、跨时区和跨午夜归属。
- 删除或修正记录后看板及时一致。
- 常用读 API 在目标数据量下 p95 小于 500 ms。
- 低速网络、空数据、部分数据和服务错误的 UI 行为可理解。

### 完成条件

- 两名非开发测试者能解释看板信息且不会误认为是医疗结论。
- 手机端核心页面无阻断级可用性或无障碍问题。

## Sprint 6：每日建议与每周计划（2 周）

### 目标

完成“记录—分析—计划—反馈”闭环，并证明 AI 不会越过产品安全边界。

### 工作项

- 每日结构化摘要和次日建议。
- 7 天摘要、每周计划草稿、编辑、确认和反馈。
- 数据证据引用、模型/Prompt/Schema 版本和成本指标。
- 规则层安全过滤、缺失数据和不确定性处理。
- Provider 超时、预算上限和降级体验。
- 合成 AI 回归评估集和危险建议红队用例。

### 本地测试

- 建议只能引用当前用户、当前授权范围内的真实摘要。
- 缺失数据时说明局限，不虚构饮食、运动或睡眠。
- 诊断、用药、极端节食、危险运动和紧急症状用例全部被拦截。
- AI 原始草稿与用户修改后的计划始终分离。
- Provider 超时、限流、无效 JSON 和内容拒绝均有安全降级。

### 完成条件

- AI 安全测试集无未接受的严重失败。
- 每条建议能显示数据区间、依据和局限。
- 关闭 AI 后，档案、记录和看板仍完全可用。

## Sprint 7：数据权利、恢复与生产加固（2 周）

### 目标

在部署前完成用户数据自主权、可恢复性和生产安全基线。

### 工作项

- 数据导出、短期私有下载和过期清理。
- 记录删除、账号删除、重新验证和备份淘汰说明。
- 同意记录版本、撤回和保留策略。
- PostgreSQL 与对象文件的加密备份、站外复制和删除清单。
- 恢复 runbook、回滚 runbook 和事件响应 runbook。
- 生产 Compose overlay、固定镜像、资源限制、健康检查和 Secret 方案设计。
- 基础监控：可用性、延迟、错误、任务积压、磁盘、备份和证书。

### 本地/隔离环境测试

- 导出只包含本人数据，链接过期且不可猜测。
- 账号删除能覆盖主数据、派生文件、导出包和待处理任务。
- 从加密备份恢复到全新隔离环境。
- 恢复后验证数据库约束、文件哈希、RLS、登录和核心烟雾流程。
- 模拟旧镜像回滚，确认数据库迁移保持向前/向后兼容窗口。
- 运行 Secret、依赖、镜像和端口暴露扫描。

### 完成条件

- 恢复演练实际达到 RPO/RTO 目标，而非只存在备份文件。
- 无未接受的高危漏洞、公开端口或硬编码 Secret。
- 生产上线清单由项目所有者逐项签字确认。

## Sprint 8：预发布与邀请制上线（1 周）

### 目标

先在与生产相同架构的预发布环境验证，再以最小用户量上线。

### 工作项

- 所有公网域名 ICP 备案已通过；上线后按时办理公安联网备案。
- 建立 staging，使用独立数据库、Bucket、OIDC Client、AI Key 和域名。
- 执行完整迁移、E2E、安全、性能、备份和恢复验收。
- 部署 production，但先只允许项目所有者账号。
- 完成生产烟雾测试后，再邀请 1 名家庭成员。
- 观察 48 小时后，无严重问题再扩大到计划中的少量家庭用户。
- 明确反馈入口、支持方式、维护窗口和事件联系渠道。

### 完成条件

- 监控、备份、证书、磁盘和任务积压告警已实际触发验证。
- 回滚步骤完成一次无数据破坏的演练。
- 所有受邀用户读过非医疗用途和 AI 数据处理说明。
- 仅当 P0 发布门槛全部通过才开始 4 周 Pilot。

## 5. 本地测试体系

本地测试不是上线前一次性动作，而是每个 Sprint 的固定层级。

| 层级 | 运行时机 | 覆盖内容 | 失败处理 |
| --- | --- | --- | --- |
| 静态检查 | 每次提交前 | 格式、类型、lint、Secret | 不允许提交 |
| 单元测试 | 每次提交前 | 规则、校验、聚合、脱敏 | 不允许合并 |
| API/数据库集成 | 每个 PR | Migration、CRUD、RLS、事务 | 不允许合并 |
| Compose 集成 | 每个 PR/每日 | 真实 PostgreSQL、MinIO、Worker | 不允许发布候选 |
| 浏览器 E2E | 每个 Sprint | 手机/桌面核心用户流程 | P0 失败阻断 Sprint |
| 安全测试 | Sprint 2 起每次发布 | 越权、会话、上传、限流、日志 | 严重失败阻断发布 |
| AI 评估 | Sprint 4 起模型/Prompt 变更 | 忠实度、安全、结构和降级 | 回归失败禁止切换模型 |
| 恢复演练 | Sprint 7、上线前、之后每季度 | 数据库、对象、删除清单、RLS | 未恢复成功禁止上线 |

### 标准本地验收流程

1. 从干净的 Git checkout 和空数据卷开始。
2. 创建仅用于本地的 Secret 和两个合成测试用户。
3. 启动完整 Compose 栈，等待所有健康检查通过。
4. 执行数据库迁移和合成种子数据。
5. 依次运行静态、单元、集成、E2E、安全和 AI 评估。
6. 手工使用真实手机访问局域网地址，走一次核心流程。
7. 检查日志和错误追踪是否出现敏感数据。
8. 停止并重启容器，验证数据持久化与任务恢复。
9. 保存测试报告，不保存真实健康内容。

### 测试数据规则

- 默认只使用合成姓名、合成记录和无身份含义的图片。
- 真实家庭数据只能在生产邀请制试运行中使用，不进入开发、CI 或截图。
- 测试数据必须同时覆盖正常、缺失、极端、跨时区和恶意输入。
- User A/User B 越权测试是长期回归集，不得在后续 Sprint 删除。

## 6. 环境与发布路径

```text
Developer laptop
  -> Pull request CI (ephemeral services)
  -> Staging server (synthetic data only)
  -> Production server (invite-only users)
```

### 环境隔离要求

| 项目 | Local | CI | Staging | Production |
| --- | --- | --- | --- | --- |
| 数据 | 合成 | 临时合成 | 持久合成 | 真实受邀用户 |
| OIDC Client | Local | Test | Staging | Production |
| 数据库/Bucket | 独立 | 每次销毁 | 独立 | 独立 |
| AI Key/预算 | 开发低额度 | Mock/限制 | Staging 限额 | Production 限额 |
| 域名 | localhost/LAN | 无公网 | staging 子域名 | 正式域名 |
| 备份 | 可选 | 无 | 恢复演练 | 加密站外备份 |

生产数据不得复制回 Local 或 Staging。

## 7. Docker 单服务器部署步骤

以下是上线 runbook 的计划版本。实际执行前需根据服务器系统、地域和供应商补全命令与负责人。

## 7.1 准备服务器与域名

建议的 MVP 起始规格：4 vCPU、8 GB RAM、80–160 GB 加密 SSD、独立站外备份。AI 使用外部 Provider 时通常足够；最终按 staging 负载测试调整。

1. 选择受支持的 64 位 Linux LTS 版本和数据地域。
2. 配置正式域名，并为 staging 使用独立子域名。
3. 创建非 root 运维用户，只允许 SSH Key 登录；关闭 root 远程登录和密码登录。
4. 开启系统自动安全更新、时间同步和磁盘空间监控。
5. 云安全组只开放：
   - `443/tcp`：正式 HTTPS；
   - `80/tcp`：仅用于跳转或证书验证；
   - `22/tcp`：只允许固定管理 IP 或 VPN。
6. PostgreSQL、MinIO API/Console、应用内部端口和监控端口不得对公网开放。
7. 特别检查 Docker 与主机防火墙的交互；Docker 发布端口可能绕过部分 `ufw` 规则，必须通过云安全组、未发布端口和 `DOCKER-USER` 链共同验证。

## 7.2 安装 Docker

1. 仅使用 Docker 官方仓库安装稳定版 Docker Engine。
2. 安装 Docker Compose plugin，不使用 legacy `docker-compose` standalone。
3. 验证 Engine 和 `docker compose` 版本。
4. 将运维用户加入 Docker 权限组前评估风险：Docker 访问等同于主机高权限；生产可选择继续使用受控 `sudo`。
5. 配置 Docker 日志轮换，防止容器日志占满磁盘。
6. 配置 daemon 和镜像拉取来源；不启用未经评估的远程 Docker API。

## 7.3 准备生产目录与 Secret

1. 生产机只保存部署清单、受控 Secret 文件和持久卷，不 bind mount 应用源代码。
2. 应用镜像由 CI 构建、扫描并推送到私有容器仓库；按不可变版本或 digest 部署。
3. 创建 production Compose overlay：
   - 生产镜像版本；
   - 资源限制；
   - restart policy；
   - healthcheck；
   - 只读文件系统和最小 Linux capabilities；
   - 仅 reverse proxy 发布 80/443。
4. 数据库密码、OIDC Secret、AI Key、备份密钥使用 Docker Compose secrets 或权限严格的独立 Secret 文件按服务授权，不写入 Git、镜像或普通环境变量日志。
5. 用 `docker compose config` 检查最终合并配置，确认无意外端口、默认密码或缺失变量。

Docker 官方建议用 production-specific Compose overlay 调整端口、环境、restart policy 和日志等生产差异；Compose secrets 会按服务挂载到 `/run/secrets/...`，降低环境变量意外泄露风险。

## 7.4 首次部署顺序

1. 在 staging 完整执行一次同样流程并记录耗时。
2. 拉取经过 CI 扫描并批准的固定版本镜像。
3. 启动 PostgreSQL 和对象存储，等待 healthcheck 通过。
4. 初始化生产数据库角色、私有 Bucket、Bucket policy 和生命周期规则。
5. 以一次性受控任务运行数据库迁移；失败时停止，不启动新应用版本。
6. 启动 API、Worker 和 Web，最后启动或切换 reverse proxy。
7. 验证所有容器健康、内部 DNS、磁盘卷和时间设置。
8. 执行生产烟雾测试：登录、本人档案、手工记录、上传、AI 失败降级、看板、退出。
9. 用第二个测试账号执行一次越权负面测试。
10. 检查普通日志、审计日志和错误追踪中无敏感正文。
11. 启用站外备份和告警，并立即执行首次备份。
12. 在隔离位置验证首次备份可恢复后，才邀请第一名用户。

## 7.5 TLS 与入口

- Reverse proxy 负责 TLS、HTTP 到 HTTPS 跳转、HSTS、请求大小限制和基础限流。
- 证书自动续期，但必须为续期失败和临近过期建立告警。
- `/health/live` 只表示进程存活；`/health/ready` 验证关键依赖，但不得返回敏感细节。
- 管理接口、MinIO Console、数据库和监控面板只能经 VPN、SSH tunnel 或受控管理网络访问。

## 7.6 日常发布步骤

1. 在本地和 CI 完成全部发布门槛。
2. 将同一镜像版本部署到 staging，运行 migration、E2E 和烟雾测试。
3. 记录当前生产镜像 digest 和数据库 migration 版本。
4. 生产变更前完成并验证最新备份。
5. 拉取新镜像，先运行向前兼容 migration。
6. 逐服务更新 API/Worker/Web，观察 healthcheck、错误率和任务积压。
7. 完成生产烟雾测试和两个用户隔离检查。
8. 观察至少 30 分钟；严重错误立即停止扩大使用并进入回滚流程。
9. 记录发布版本、时间、执行人、migration 和验收结果。

## 7.7 回滚策略

- 应用回滚：切回上一已知良好镜像 digest，重新创建受影响服务。
- 数据库：优先采用兼容 migration 和 forward fix，不把数据库回滚作为默认手段。
- 破坏性 Schema 变更采用“扩展—迁移—收缩”，至少跨一个发布窗口。
- 只有数据损坏或不可恢复迁移才从备份恢复；恢复会造成 RPO 范围内的数据丢失，必须明确批准。
- 每次发布前都验证旧版本能在新 Schema 的兼容窗口内运行。

## 7.8 备份与恢复

- PostgreSQL：至少每日加密逻辑/物理备份，并复制至不同故障域。
- 对象存储：版本化或增量复制，保留数据库引用与对象的一致性信息。
- Secret/密钥：单独备份和访问控制，不与数据备份放在同一权限域。
- 恢复演练：上线前一次，之后至少每季度一次。
- 恢复验收：约束、记录数量、文件哈希、RLS、登录、核心流程和删除清单全部通过。
- `docker compose down -v` 会删除命名卷，生产 runbook 中禁止使用，除非明确执行受批准的数据销毁。

## 8. 上线 Go/No-Go 清单

只有全部回答“是”才能上线：

- [ ] P0 功能和失败路径全部验收。
- [ ] 两用户越权自动化和手工测试通过。
- [ ] AI 危险建议与虚构数据回归测试通过。
- [ ] 生产仅暴露 80/443 和受限 SSH。
- [ ] 数据库、对象存储和管理界面公网不可达。
- [ ] 所有 Secret 未进入 Git、镜像、日志或错误追踪。
- [ ] 固定版本镜像通过依赖和漏洞扫描。
- [ ] 生产备份成功，隔离恢复演练通过。
- [ ] 监控、证书、磁盘、错误率、任务积压和备份告警验证通过。
- [ ] 回滚步骤和上一镜像 digest 已记录。
- [ ] 隐私说明、AI 同意、导出和删除流程可用。
- [ ] 用户明确了解产品不是医疗诊断或紧急服务。

任一安全、隔离、恢复或数据权利项不通过即为 No-Go，不能以“家庭内部使用”为理由跳过。

## 9. Pilot 期间的扩量规则

### 第 1 周

仅项目所有者使用，验证日常记录、AI 费用、磁盘增长、备份和告警。

### 第 2 周

增加 1 名家庭成员；重点观察登录、隔离、手机体验和支持问题。

### 第 3–4 周

如果前两周无严重安全或数据完整性事件，再扩大到计划中的小范围用户。每周复盘：

- 激活与记录完成率；
- 饮食 AI 修正率；
- 建议有用/不适用反馈；
- API/AI 延迟与失败；
- 任务积压、磁盘、备份和恢复验证；
- 隐私疑问和误解。

Pilot 期间不增加体检报告、设备、家庭共享、付费或医疗功能。只修复 P0 问题和改善核心流程。
