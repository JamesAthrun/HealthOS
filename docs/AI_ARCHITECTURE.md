# HealthOS AI 架构 v0.1

## 1. AI 的产品角色

AI 用于减少录入成本、整理趋势和起草行动建议。AI 不拥有事实最终决定权，不进行医疗诊断，不替代专业人员。正式统计使用用户确认数据。

## 2. 三类能力

| 能力 | 输入 | 输出 | 必须人工确认 |
| --- | --- | --- | --- |
| 饮食识别 | 去标识化餐食图片 | 食物、份量和营养估算 | 是 |
| 每日建议 | 当日确认记录和昨晚睡眠摘要 | 少量次日行动建议 | 用户选择执行 |
| 每周计划 | 7 天聚合趋势、目标和限制 | 可编辑的饮食/运动/睡眠计划 | 保存前确认 |

## 3. 数据最小化

### 饮食识别

发送：完成识别所需的图像和必要的语言/单位偏好。

不发送：姓名、邮箱、精确位置、家庭关系、完整档案、历史病历。上传后移除非必要 EXIF；界面提醒用户避免拍入人脸、药盒标签和身份信息。

### 规划

发送结构化摘要，例如每天总量范围、记录完整度、运动分钟、睡眠时长趋势、本人目标和相关限制。不发送原始照片、完整自由文本、账号标识和不相关历史。

## 4. 请求管线

```text
Authorize purpose and user
  -> verify current consent/policy version
  -> build minimum typed input
  -> redact and validate
  -> select provider/model by policy
  -> call with timeout and no provider-side training where contractually available
  -> parse strict structured output
  -> run safety and business-rule validation
  -> persist versioned draft and provenance
  -> present limitations and request confirmation
```

任何一步失败都返回安全状态，不把未验证文本直接写入正式记录。

## 5. 结构化输出

每项能力定义版本化 JSON Schema/Pydantic 模型。示例建议项：

```json
{
  "schema_version": "1.0",
  "summary": "...",
  "actions": [
    {
      "category": "sleep",
      "action": "Try to start winding down 30 minutes earlier.",
      "rationale": "Sleep duration was below your target on 4 of 7 recorded nights.",
      "evidence_refs": ["sleep_trend:2026-10-22/2026-10-28"],
      "confidence": "medium"
    }
  ],
  "limitations": ["Two meal records were incomplete."]
}
```

服务端拒绝未知结构、超长内容、无证据引用和违反安全规则的输出。展示层不得把模型生成的引用伪装成医学证据。

## 6. 安全策略

生成前后均执行规则检查：

- 禁止诊断、用药/停药、紧急状况处置替代专业建议。
- 禁止极端节食、惩罚性运动、自伤或危险挑战。
- 对孕期、未成年人、进食障碍提示、严重症状等高风险上下文，不生成个性化限制方案，改为安全边界提示和专业支持建议。
- 对记录不足、冲突或异常值明确表示不确定。
- 不以 AI 内容覆盖用户已确认事实。

紧急提示必须采用产品预先审核的确定性文案，而不是临时由模型自由生成。

## 7. Provider Adapter

统一接口隐藏供应商 SDK，配置包括：

- 允许的用途与数据地域
- 模型别名和版本锁定
- 超时、重试、并发和预算
- 数据保留、训练使用和日志政策
- 是否允许图片、敏感数据类别和本地模型回退

业务数据库保存内部别名和必要来源信息；密钥只从 Secret 管理加载。更换模型前需跑离线评估，不直接在生产切换。

## 8. 提示与版本管理

- Prompt 模板放在代码仓库并做评审，运行记录保存版本哈希。
- 系统指令、Schema 和安全规则不可由用户输入覆盖。
- 自由文本视为不可信输入，使用清晰数据边界，防止提示注入影响工具或权限。
- 模型无权直接调用数据库、发消息、删除数据或创建分享权限。
- 任何未来工具调用必须使用服务器端白名单和二次授权。

## 9. 评估

### 饮食识别

- 食物识别 top-k 覆盖率。
- 用户修正率与热量/宏量营养绝对误差。
- 对常见中餐、混合菜、汤和份量不明场景分组评估。
- 低置信场景是否恰当地询问或提示手工录入。

### 建议与计划

- 数据忠实度：不得虚构记录。
- 可执行性：动作具体、现实、非极端。
- 个性化：只使用允许的数据。
- 安全性：红队用例违规率为 0 发布门槛。
- 稳定性：同类输入的核心约束一致。
- 用户反馈：有用/不适用/不安全。

评估集使用合成或明确授权且去标识化的数据，不把真实家庭数据放入 Git。

## 10. 可观测性与保留

记录模型别名、模板版本、Schema 版本、延迟、Token/成本、状态、失败代码和安全过滤结果。普通日志不记录原始输入输出。若为质量评估保留样本，必须有明确目的、访问控制、加密、同意和自动到期。

## 11. 降级策略

- 图片模型失败：允许手工添加食物。
- 输出解析失败：有限次数修复/重试，仍失败则不展示原始文本。
- Provider 超时：任务保持可重试状态并通知用户稍后查看。
- 规划安全校验失败：不展示，记录去敏错误码并使用确定性通用建议或无结果状态。
- 达到预算：暂停非关键自动生成，保留手工记录和用户主动操作的清晰说明。
